# Release notes: TLS discovery and reconnect, version 2.26.5

These are my notes on the changes I made for the TLS discovery and reconnect rules (ADR-40): how the client treats the servers a cluster advertises, how it verifies them over TLS, how it reconnects, and what it writes in events and errors. Each item says what the client did before, what it does now, and the option that restores the old behavior where there is one. They go into the changelog for the release that carries them; until then this file is the reference.

1. **Discovered servers are `host:port` entries only.** `ServerPool.acceptDiscoveredUrls` now receives the list as `host:port`, with an IPv6 address in brackets, the way nats-server writes it. The user info of an entry is dropped before the call, and an entry that carries a scheme, that does not parse as `host:port`, or whose port is outside 1 to 65535 is left out and reported through the error listener's `discoveredServerSkipped`. If you wrote a custom pool that took the scheme from the entry, take it from the `origin` of the two-argument overload instead: a discovered server is dialed with the transport and the TLS of the server that reported it, never with a transport the entry names. The pool receives the list whether or not `ignoreDiscoveredServers()` is set, so a custom pool honors that option itself, as `NatsServerPool` does.

2. **The `DISCOVERED_SERVERS` event carries the normalized list.** The detail of `Events.DISCOVERED_SERVERS` is the `host:port` list as accepted: user info dropped, leading zeros removed. Before, it was the raw `connect_urls` text.

3. **A mixed bootstrap list no longer changes the scheme of a discovered server.** With a bootstrap list that mixes transports, a server discovered through `nats://a` is listed and dialed as `nats://`. Before, it took the first non-`nats` scheme in the list.

4. **An ip-address seed with an ip-address cluster needs an option now.** If you connect by ip address to a cluster that advertises ip addresses and your certificates carry those addresses, the discovered servers are now skipped and reported through `discoveredServerSkipped`, and there is no failover to them. Set `tlsVerifyDiscoveredByIp()` to verify them against their ip addresses, or `tlsServerName` to verify every server against one name. Before, a discovered ip address was verified as one without being asked.

5. **A discovered ip address inherits the seed's hostname over any number of hops.** A server discovered by ip address from a server that was itself discovered by ip address from a hostname seed is verified against that hostname. Before, the second hop failed.

6. **The name-check failure is a different exception.** It is an `SSLHandshakeException` whose message starts with the client's own text, naming the host it expected and where that name came from, and quotes the JDK's message. A `startsWith` or equality check on the old JDK message breaks; a `contains` check does not. The `IOException` the initial connect throws now has that failure as its cause.

7. **`maxReconnects` holds during an outage.** When the servers of a cluster keep naming each other in their INFOs while they are down, the connection now closes once every server reached `maxReconnects`. A server that reached its limit, configured or discovered, is not brought back by a later INFO while the connection lasts, and the counts accumulate across the reconnects of one connection. Before, every INFO that named the server again reset it, and the reconnect went on without end. `maxReconnects(-1)` keeps reconnecting forever, as before.

8. **Jitter.** A reconnect jitter of zero works. A negative jitter is refused by the builder; before, it was accepted and misbehaved.

9. **The addresses of one hostname share one connection timeout.** When a hostname resolves to several addresses, they are tried in turn within one connection timeout, the attempt's budget. Before, each address had a timeout of its own. A first address that black-holes now uses the budget up and fails the attempt where the next address used to be reached after one timeout; the next attempt starts with the next address. If you depend on reaching a later address within one attempt, raise `connectionTimeout` or use `ResolveToFirst`.

10. **A failed attempt fails faster, and a hung lookup does not hold the reconnect.** A server that answers `-ERR` and closes fails the attempt at once, with the cause "The server ended the attempt with an error: ..."; before, the attempt waited out the connection timeout. A WebSocket upgrade that hangs fails the attempt at the connection timeout. A name lookup runs under a timer of its own, the connection timeout, and a lookup that fails or runs out of time is a failed attempt of that server, reported through `exceptionOccurred` and counted toward the server's limit; before, a lookup held the reconnect for as long as the resolver took. The lookup runs on the connection's `executor`, beside the data port's connect, so a fixed pool you supply must have room for them.

11. **Malformed input on an established connection is reported, not fatal.** An INFO that does not parse is skipped and reported through `exceptionOccurred` as an `IllegalArgumentException` that quotes it. A header block that does not parse drops its message, with a report. Before, either one ended the connection.

12. **Url passwords are hidden.** The `uriDetails` of connection events, the text of the connect failure, the trace lines and the `serverRejected` string no longer carry the password of a url, and so no longer equal `getConnectedUrl()` or `getServers()` for a credentialed url; `getConnectedUrlRedacted()` gives the hidden form. `Options.Builder.servers` throws a different message for a url that does not parse, without its credentials. Code that compared an event's detail with `getConnectedUrl()` must compare with `getConnectedUrlRedacted()`.

13. **TLS 1.2 is the floor.** Every connection enables TLS 1.2 and above only, whatever the context enables, and the contexts the client builds offer TLS 1.3. A server that offers only TLS 1.0 or 1.1 now fails on every context. `Options.DEFAULT_SSL_PROTOCOL` is now `TLS`; it is a compile-time constant, so code compiled against an earlier jar keeps `TLSv1.2` inlined until it is rebuilt, which changes nothing in what is negotiated.

14. **`ignoreAuthErrorAbort()` is new.** By default, as before, the second identical authorization error from one server ends the reconnect and the connection closes. With `ignoreAuthErrorAbort()` on the builder, or the property `io.nats.client.ignore.auth.error.abort`, the reconnect goes on; use it when credentials are rotated on the servers while clients run.

15. **A TLS upgrade whose handshake is not confirmed fails the attempt.** When the handshake-completed notification does not arrive within the connection timeout, the attempt fails and nothing is written on the connection. Before, the failure was reported and the attempt went on in plaintext until its first PING. No known trigger; noted for completeness.
